# foxy-customer-portal

A drop-in customer portal: sign-in, access recovery, self-registration,
temporary-password reset, and account management.

```html
<foxy-customer-portal store-domain="demo"></foxy-customer-portal>
```

## Attributes

| Attribute             | Required | Default                    | Notes                                                                                                                                    |
| --------------------- | -------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `store-domain`        | yes      | —                          | `demo` becomes `demo.foxycart.com`; a value with a dot is used as-is, so custom domains work.                                            |
| `template-set-id`     | no       | store default              | Picks the template set, which decides both the language strings and the locale. Omit it and the store's default set is used. Also reserved for future payment-method editing. |
| `skip-password-reset` | no       | `false`                    | Suppresses the forced reset screen after signing in with a temporary password.                                                           |
| `url-sync`            | no       | `false`                    | Reflects the current account sub-page into the host page's URL (`fc_page`/`fc_id` query params) and drives navigation from Back/Forward. |
| `variant`             | no       | `subscriptions`            | Which selling shape the account screen is laid out for — see [Variants](#variants). An unrecognised value falls back to `subscriptions`. |

The embed origin is not an attribute — it comes from `VITE_EMBED_ORIGIN` at
build time.

`lang` is not an input. The portal takes its language from the template set,
and writes the resolved locale onto its own content instead. Setting `lang` on
the element has no effect on what language it renders.

## Events

| Event           | Detail                                 |
| --------------- | -------------------------------------- |
| `signin`        | none                                   |
| `signout`       | none                                   |
| `passwordreset` | `{ result: "skipped" \| "completed" }` |

## Variants

`variant` picks the layout for the store's selling shape. It changes the
account screen only; sign-in, recovery and the profile, password and address
pages are identical in both.

| | `subscriptions` (default) | `orders` |
| --- | --- | --- |
| Subscriptions section | shown | not rendered |
| Payment history section | shown, headed "Payment history" | shown, headed "Orders" |
| Its presentation | dense rows | cards with item images |
| Transaction types listed | excludes `subscription_renewal` | includes it |
| Empty payment history | section renders nothing | section keeps its heading and says "No payments yet." |

```html
<foxy-customer-portal store-domain="demo" variant="orders"></foxy-customer-portal>
```

Two things the orders variant deliberately does not change:

- **Subscription pages stay reachable.** There is no link to one from the
  account screen, but a bookmarked or emailed subscription URL still resolves,
  and `url-sync` still routes to it. Hiding an entry point is not retiring a
  route.
- **Renewals become visible in the list.** The subscriptions variant leaves
  `subscription_renewal` transactions to each subscription's own payment
  history. With no subscriptions section, that page has no entry point, so the
  orders variant lists renewals in that section instead — otherwise a
  renewal charge would appear nowhere in the portal. Card-update
  (`updateinfo`) records stay excluded in both.

## What the order page shows

The order page reads three things beyond the transaction itself, each from its
own rel, fetched only when that page opens — the orders list request is not
enlarged to carry them:

| Panel | Source | Notes |
| --- | --- | --- |
| Items | `fx:items` (embedded via the list's `items:item_options` zoom) | Options, weight and code honour `cart_display_config`. Ten per page. On a multiship order — two or more distinct `shipto` values — the list is grouped under each destination, with headings matching the shipment names below. A single-destination order stays a flat list. |
| Payment method | `fx:payments` | The card **actually charged** — brand, last four, expiry — not the customer's current default payment method, which may since have changed. A purchase order shows its number. A payment type the portal has no customer-facing name for (`amazon_mws`, `ogone`, `hosted`) shows no row rather than leaking the enum. |
| Shipping | `fx:shipments` | The delivery address and the service chosen at checkout, one row per shipment so multiship orders read correctly. What each shipment cost goes in the summary rail, not here. |

Both `fx:payments` and `fx:shipments` are narrow, customer-safe projections:
the Customer API allow-lists their fields and exposes no gateway internals,
carrier accounts or negotiated rates. An order linking to neither — an older
API response, or a digital order paid through an unnamed gateway — renders no
Billing & shipping panel at all.

## Notes

## Language

Every string comes from the API, at `<store base>/s/customer/language_strings`.
The store's own overrides are already merged in, so a store customizes the
portal by editing its language strings — not by setting attributes. Two
attributes that used to do this job, `full-name-template` and `lang`, are gone.

The customer's name is one of those strings: `portal_header_full_name`,
`{firstName} {lastName}`. Reorder the placeholders for a locale that leads with
the family name, or prefix a salutation.

The portal waits up to 3 seconds for that request on first paint. If it fails,
times out, or the store has no strings for a key, the portal renders that
string's built-in English rather than failing — so a slow or missing endpoint
costs a language, never the portal.

## Notes

Session data is stored under a key namespaced by store domain, so two Foxy
stores served from one origin do not share a session.

Self-registration appears only when the store enables it. It requires an
hCaptcha challenge, which loads a script from `js.hcaptcha.com`.
